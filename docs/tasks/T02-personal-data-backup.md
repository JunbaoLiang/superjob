# T02 — 个人数据与冻结历史材料备份

状态：`complete`
优先级：P0
正式项目目录：`<project-root>`
备份根目录：`<backup-root>`（仓库外、位于本机受 FileVault 保护的磁盘）

## 1. 目标

创建一份可校验、可恢复的本机备份，覆盖当前候选人档案和全部岗位数据，包括已投递/被拒的冻结历史材料。备份必须保留源文件内容和层级；不得改写、移动或删除源数据。

T02 不更新候选人档案、不重新生成材料、不修改岗位状态、不上传云端，也不将个人数据加入 Git。

## 2. 已确认输入

- 备份源仅限 `<project-root>/data/profile/` 与 `<project-root>/data/jobs/`。
- 已投递和被拒岗位连同当时材料是冻结历史记录，必须保持字节不变。
- 备份创建在仓库外的时间戳目录：`<backup-root>/superjob-YYYYMMDD-HHMMSS/`。
- 本机 FileVault 已开启；首份本机备份可依赖 FileVault，不另建加密容器。
- 复制到外接磁盘、公共云盘或非 FileVault 位置前必须停止，并由用户单独选择加密方式。

## 3. 授权边界

只有用户明确回复“授权执行 T02-A”后，才可创建备份目录和复制文件。

允许：

- 在 `<backup-root>` 下创建一个此前不存在的时间戳备份目录及临时 staging 目录。
- 读取源文件；复制源文件到 staging；在完成后做一次源/备份 SHA-256 比对，并写入备份清单、校验结果和恢复说明。
- 在验证通过后将 staging 原子改名为最终备份目录。

禁止：

- 修改、删除、移动、重命名源文件或岗位目录。
- 覆盖已有备份目录。
- 读取、输出或写入个人数据正文到 Git、聊天记录、日志或公共服务。
- 上传、同步或推送备份；复制到任何未确认受 FileVault 保护的位置。
- 在本任务中 commit、push、部署或更改产品代码。

## 4. 备份内容与目录结构

最终备份目录只包含：

```text
superjob-YYYYMMDD-HHMMSS/
├── profile/                 # data/profile/ 的完整副本
├── jobs/                    # data/jobs/ 的完整副本
├── MANIFEST.sha256          # 源/目标相对路径与 SHA-256 校验值
├── INVENTORY.txt            # 文件数、目录数、大小与生成时间
└── RESTORE.md               # 只读恢复说明
```

目录权限应仅限当前用户读取和写入（创建时使用 `umask 077`；验证最终目录权限）。备份清单本身含文件名，应与备份放在同一受保护目录，且不进入 Git。

## 5. 执行步骤

### 步骤 1 — 只读预检

1. 确认源目录仍为 `<project-root>/data/profile/` 和 `<project-root>/data/jobs/`。
2. 确认 FileVault 仍为开启状态。
3. 确认 `<backup-root>` 位于本机受保护磁盘、不是仓库子目录、不是符号链接到云同步目录，并且不存在同名最终备份目录。
4. 以源文件总大小的至少两倍作为可用磁盘空间下限；空间不足即停止。
5. 记录源目录的文件数和总大小，作为空间与完成后的库存基线；不打印文件正文。

### 步骤 2 — 创建受限 staging 备份

1. 用当前时间生成唯一的目标名；目标已存在时停止，不覆盖、不复用。
2. 在 `<backup-root>` 下创建权限为 700 的 staging 目录。
3. 使用标准 archive 模式（保留层级、时间戳、权限和隐藏文件）将 `profile/` 与 `jobs/` 分别复制到 staging。macOS 的扩展属性复制仅在单独验证兼容性后启用；SHA-256 清单是内容完整性的权威依据。
4. 复制期间不写入源树；不调用 LLM、浏览器扩展、网络服务或 Git。

### 步骤 3 — 校验与完成

1. 复制完成后，为源和 staging 分别生成按相对路径排序的 SHA-256 清单。
2. 比较两份清单：文件数量、相对路径和每个 SHA-256 必须完全相同。
3. 执行一次标准 archive-mode dry-run，确认权限和时间戳没有待同步的差异。
4. 将通过的清单、库存信息和恢复说明写入 staging。
5. 原子改名 staging 为最终备份目录；之后将最终目录设为用户专用权限。
6. 最终确认根仓库 `git status` 未出现个人数据变化或暂存项。

## 6. 验收标准

- 备份位于仓库外且所在磁盘 FileVault 已开启。
- 最终目录是新建且唯一的时间戳目录；没有覆盖任何已有文件。
- `profile/` 和 `jobs/` 的一次源/目标 SHA-256、相对路径和文件数完全一致。
- 标准 archive-mode dry-run 没有待同步差异；源数据从未被本任务写入，尤其是冻结历史材料。
- 备份权限仅限当前用户；备份内容、清单和恢复说明都不在 Git 状态中。
- 可从 `RESTORE.md` 理解如何在单独的新目录中恢复；T02 本身不执行覆盖式恢复。

## 7. 停止条件

任一项触发即停止并报告：

- FileVault 关闭、无法验证，或目标不是确认的本机受保护磁盘。
- 目标目录已存在、路径解析不明确、目标位于项目仓库内，或可能指向云同步目录。
- 可用空间不足、源文件不可读、复制失败，或任一清单不匹配。
- 源数据在复制过程中发生变化。
- 需要覆盖、删除、移动、上传、同步或更改 Git 状态才能继续。

## 8. 恢复与事故处理

- 恢复仅能在用户单独授权后进行，并且必须先恢复到一个新目录；不得直接覆盖活跃 `data/`。
- staging 校验失败时，保留 staging 以便诊断，不触碰源数据；不把失败目录标为完成备份。
- 发现备份位置不再受 FileVault 保护时，停止使用该备份位置并由用户决定加密迁移方案。

## 9. 完成后的交付格式

执行者必须报告：

1. 最终备份目录（不在公开文档或 Git 中记录完整路径）
2. 源/目标文件数、大小和 SHA-256 比对结果
3. FileVault 与目录权限验证结果
4. 源历史材料未变化的证据
5. 失败或遗留风险
6. 下一张建议任务卡：T03 — 更新 2027 候选人档案
