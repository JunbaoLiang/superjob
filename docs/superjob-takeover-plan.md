# Superjob 接手与改造路线图（公开版）

版本：1.0
状态：决策已确认；按任务卡逐项执行

## 目标

Superjob 是一个个人求职操作系统，帮助用户更快完成职位发现、筛选、定制材料、质量审核、导出、投递追踪和面试准备。系统不编造经历，不自动提交申请、发送外联或删除历史记录；所有不可逆的对外操作都保留给用户确认。

## 工程原则

1. 事实优先：候选人主简历是唯一事实来源；事实核查失败不得显示为 clean。
2. 历史保护：已投递和被拒的岗位材料冻结保存，不被新版档案覆盖。
3. 草稿与可投分离：草稿可以生成和预览，只有通过质量闸门或有可追溯人工 override 的材料才能标记为 ready。
4. 本地优先：先恢复可靠的本地闭环，再部署云端。
5. 最小暴露：密钥、真实档案、岗位原文、投递材料和本机状态默认不进入 Git。
6. 每步可回滚：先建立基线和备份，再进行高风险改动；不混合多个高风险操作。
7. 不自动对外行动：系统提高判断和材料生产效率，用户保留最终提交权。

## 已确认的产品与工程决策

| 决策 | 结论 |
|---|---|
| 项目目录与 Git | 本地项目目录为唯一正式目录；公开 GitHub 仓库只保存通用代码与去个人化文档。 |
| 数据与历史 | 已投递/被拒材料冻结；个人数据保留在本地并建立校验备份。 |
| 本地与云端 | 短期本地主用；安全、迁移和恢复验证完成后，云端主用且本地副本保留。 |
| 质量放行 | 事实核查失败、存在 unresolved issue、页数未知或超过一页时为 `needs-review`；人工 override 必须保留原因与问题快照。 |
| 双状态模型 | 投递进度与材料 readiness 独立；材料 ready 并经用户最终确认前，不能标记为已投递。 |
| 评分 | Eligibility 与 Match 分离；明确不合格才 hard block；未知 sponsorship 需要核实而不是默认跳过。 |
| 评分阈值 | 主投阈值为 75，海投阈值为 60；stretch 岗位由用户点选后才生成材料。 |
| 职位来源 | 优先批量 URL 导入、去重和失败重试；剪贴板多 JD 为补充；不自动申请。 |
| 功能优先级 | 暂停 Notion；面试模块在岗位进入 interview 后实施；先完成质量闸门、失败可见性和编辑持久化。 |

## 路线图

### 阶段 A — 安全基线

- T01：建立公开 Git 安全基线。当前进行中；commit 和首次公开 push 需要单独授权。
- T02：备份个人档案和历史材料，保存文件清单和校验值，不上传到 Git 或公共云盘。

### 阶段 B — 候选人事实与历史规则

- T03：更新本地候选人档案与求职窗口；所有事实均由用户确认。
- T04：区分冻结历史材料和按当前档案准备的活跃岗位材料。

### 阶段 C — 本地稳定版

- T05：建立不调用真实 LLM 的自动化测试基线。
- T06：修复零终端服务、安装器、日志和健康检查。

### 阶段 D — 投递质量闸门

- T07：为模型输出增加结构和类型校验，解析失败必须显式失败或重试。
- T08：实现 readiness、人工 override、最终材料确认和投递前阻断。
- T09：仅重新处理活跃岗位；冻结历史材料不自动覆盖。

### 阶段 E — 命中率与吞吐量

- T10：拆分 eligibility 与 match，并离线比较历史评分。
- T11：实现批量 URL/JD 导入、去重、筛选队列和失败重试。
- T12：在本地记录求职效果指标，不上传第三方。

### 阶段 F — 体验、安全与云端

- T13：改进看板工作流，包括 readiness 标识、失败任务与材料版本提示。
- T14：加固 Markdown 渲染、链接、扩展权限、token 存储和 CSP。
- T15：统一本地与云端的核心逻辑、Prompt、schema 和测试。
- T16：在单独授权下部署、迁移和验证云端；不删除本地数据。

### 阶段 G — 面试闭环

- T17：当岗位进入 interview 后，基于实际提交的材料和 JD 生成可编辑的面试准备内容。
- T18：仅在现有看板无法满足协作需求时重新评估 Notion。

## 当前执行规则

每张任务卡都必须限定修改范围、保护无关改动、先验证再实现、运行验收命令，并报告改动、验证、遗留风险和下一张任务卡。除非任务卡获得明确授权，Codex 不会提交、推送、部署、申请职位、发送消息或删除数据。
